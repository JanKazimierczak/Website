A market dashboard with no build step and no dependencies

Roughly 4,700 lines of vanilla JavaScript that pull public market data through a chain of fallbacks, draw their own charts in SVG, and degrade in the open when a source goes down.

Brief

Read the market without handing over an account.

Most market interfaces want a login, ship a megabyte of framework, and rent you the chart. I wanted the opposite: a page I could open from a bookmark, that stored nothing about me, and whose entire behaviour I could read in one file.

That constraint drove the whole design. No account means no server, which means no API keys, which means the data has to come from public endpoints reachable from a browser. No server also means no backend to cache in, so the caching, the retries, and the failure handling all had to live in the client.

The project is useful to me as a tool. It is on this site because the interesting part is not the finance — it is what a browser can be made to do with no dependencies and no privileged access, and where that approach runs out.

System

Four layers, all running in the tab.

  1. 01

    Fetch

    Quotes, histories, and profiles are requested from public endpoints. Because none of them send CORS headers to a static site, each request is routed through a public reader proxy.

  2. 02

    Fall back

    Every source is a chain rather than a single call: alternate proxies, alternate response shapes, then an alternate provider. A dead link degrades one panel instead of the page.

  3. 03

    Cache

    Responses are held in sessionStorage with per-source expiry, so switching symbols and ranges re-renders from memory instead of re-requesting.

  4. 04

    Render

    Panels are rendered from plain template strings. Price history is drawn by a hand-written SVG renderer — axes, gridlines, path, and hover read-out — with no charting library.

What is built

Two working surfaces over one data layer.

DashboardQuote board · chart · news

Open, VWAP, previous close and related metrics, a seven-range price chart, company profile, and a headline feed on a timed refresh.

Discovery scannerNine screens

Top movers, most active, earnings radar, pullback watch, value watch, IPO watch, catalyst news, focus list, and a combined summary.

Chart7 ranges, 1D to 5Y

Intraday through five years, each range mapped to the interval the upstream source actually serves.

Payload0 third-party scripts

No CDN, no framework, no bundler. The pages load their own CSS and JS and nothing else.

The hard part

Making an unreliable data layer fail quietly.

A public proxy is not a service you have a relationship with. It rate-limits without warning, changes response envelopes, and sometimes just stops. Early versions of this dashboard showed that honestly and unhelpfully: one bad request and a panel would sit empty with no explanation.

The fix was to treat every fetch as expected-to-fail. Requests carry an abort timeout so a hanging proxy cannot stall a panel. Each source is tried through more than one transport, and where two providers publish comparable data, the second is tried before the panel gives up. Panels that cannot resolve say so, and the rest of the page keeps working.

That is the part I would defend in a review. The finance is incidental; the structure is a client-side system designed around the assumption that its inputs are not dependable.

What this does not claim

A personal tool, not a financial product.

  • It is not investment advice and carries no guarantee of accuracy. Figures are whatever the upstream sources return, unaudited and unreconciled.
  • Data reaches the page through public reader proxies that can rate-limit, change format, or disappear. When that happens the affected panel will report that it could not load, and the page may look incomplete through no fault of the code.
  • Quotes are delayed and depend entirely on the upstream provider. Nothing here is real-time or exchange-grade.
  • There is no test suite and no error reporting. Failures are visible in the interface but are not recorded anywhere.
  • The honest next step is a small cached backend of my own. That would remove the proxy dependency and make the data layer something I actually control — at the cost of the "no server" constraint the project was built around.
