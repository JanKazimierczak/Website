Evidence-led portfolio system

An accessible static publishing system designed to present engineering claims alongside the reports, calculations, images, code, context, and limitations needed to evaluate them.

Publishing problem

Technical work loses value when its evidence becomes decoration.

The source material was heterogeneous: long reports, one-page briefs, calculation sheets, prototype images, CAD views, test outputs, and statements with different levels of certainty.

The system needed to make the work easy to scan without flattening team context, predictions, measurements, and unresolved facts into the same kind of claim.

Publishing pipeline

Evidence moves through four stages before release.

  1. 01

    Inventory

    Connect each project statement to an available report, calculation, image, prototype result, code repository, or explicit source limitation.

  2. 02

    Structure

    Translate the material into a consistent route from problem and methods to results, limitations, artifacts, and reflection.

  3. 03

    Validate

    Check document landmarks, links, image alternatives, external-link safety, CSS safeguards, and known factual overstatement risks.

  4. 04

    Publish

    Assemble approved routes and artifacts into a production directory, generate discovery metadata, and prepare the validated build for custom-domain publication.

Engineering decisions

The architecture stays simple so the evidence can remain complex.

The system avoids a framework runtime and database because the portfolio does not need them. Static delivery makes project artifacts durable, fast to open, and easy to archive.

01 / Integrity

Unverified facts stay out of production.

A source-only register records unresolved dates, roles, metrics, and profile details. Validation also blocks several known overstatement patterns in the project pages.

02 / Access

Interaction remains optional.

Skip links, semantic landmarks, visible focus states, reduced-motion behavior, keyboard-operable dialogs, descriptive image text, and readable static content support more ways of using the site.

03 / Continuity

Old routes fail forward.

Legacy links point to current case studies, a custom 404 provides a useful recovery path, and the sitemap, canonical metadata, and custom domain establish one public source of truth.

Content model

Claims and artifacts stay adjacent.

The same structure supports a numerical result, an observed failure, or an incomplete prototype without pretending those outcomes are equivalent.

CLAIM

State exactly what happened.

Calculated prediction, measured observation, requirement, and recommendation receive distinct labels.

CONTEXT

Keep the conditions visible.

Course, team context, test setup, sample size, assumptions, and known conflicts remain close to the result.

EVIDENCE

Make deeper inspection one click away.

Reports, code, calculations, CAD, images, tables, and interactive interfaces support the narrative.

LIMIT

Say what the evidence cannot prove.

Missing measurements, subsystem-only results, and proxy-test constraints are presented as engineering information.

Outcome

A portfolio that can be read quickly—and audited slowly.

  • The project library separates team coursework from independent systems while preserving one visual and editorial standard.
  • Every portfolio and case-study route is directly addressable, responsive, and indexable without a client-side application boot sequence; the market tool is explicitly JavaScript-dependent.
  • The build and validation steps turn content quality, accessibility safeguards, links, metadata, and release completeness into repeatable checks.
